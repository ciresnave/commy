## Ideas swept
1. A shared-memory service is an unstructured memory-mapped file created zero-filled at a requested size (rounded to whole pages); the server writes no header, allocator or bookkeeping into it, so the meaning of the bytes belongs entirely to the programs sharing it.
2. A same-machine client is offered direct mapping of the service file only if (a) an administrator opened the service to local mapping and (b) the client holds a write grant, because the server cannot observe stores into a mapping.
3. Proof that a remote-looking client shares the server's filesystem: the server writes a per-connection random nonce to a side file in the tenant directory (never in the service file), the client reads it and echoes it over the already-authenticated network connection, and the server deletes it on first use; stale unconfirmed nonces are swept by TTL and each session is capped on outstanding nonces.
4. Clients that do not share the filesystem hold a byte-for-byte mirror: one full resync of the file, then only the changed byte ranges (with the bytes) per flush.
5. A flush from any member is forwarded to every other member of the file: locally mapped members receive range descriptors only (they already see the stores), mirror members receive ranges plus bytes read from the file at forwarding time, split into frames of bounded payload; ranges are sorted and overlapping/adjacent ranges merged into a minimal list first.
6. Write ordering is assigned by the server: one sequence number per flush, stamped on every range frame of that flush, giving all mirrors a single total order of changes to a file.
7. Changed ranges in a locally mapped file are detected by trapping page-faults (write detection via the dirty-ranges crate), with a scan-and-compare fallback.
8. Live replacement of a service's backing file ("rotation") with a drain barrier: on resize, every member flushes and acknowledges on the old file (stragglers dropped at a deadline) before the requester fills a new file, then commits or aborts; only the requester may answer, once, and only after the new file is prepared.
9. Revoking a client's access to a service forces a rotation of that service's file (the file moves to a new name/location) and drops the revoked client, so a client that retained a mapping or path of the old file loses all access to later data; revocation rotation bypasses the spacing and rate limits but remains one-at-a-time per service.
10. Rotation abuse limits: minimum spacing between rotations of one service and a cap on rotations started per requester per time window, with the spacing configurable at runtime.
11. Access control as per-client, per-tenant, per-service grants with actions read/write/resize/admin where admin implies all and write implies read; a tenant-wide grant is shorthand for every service, and removing one service from a client holding only a tenant-wide grant is stored as a deny on that service that is evaluated before any grant.
12. Authentication-supplied permissions are imported as tenant-wide grants so every service check goes through the single grant engine (additive, idempotent).
13. The authenticated identity is taken from the credential's subject, never from what the client claims; a development verifier that trusts the client is enabled only by an environment switch that the configuration file is forbidden to set.
14. Grant changes are kept as an operation log and periodically compacted into a snapshot (every N changes) that restores the full grant state, with durable storage and fail-closed recovery.
15. Hash-chained, append-only audit log of server events: verification detects modification, insertion and reordering of retained events; the chain head can be exported to detect truncation; write failures are counted and never block the audited operation.
16. Hot reload of server configuration by polling the file's modification time and size: the whole file is parsed and validated; an invalid file (syntax, unknown key, forbidden key) is rejected whole and the old settings kept; only a whitelist of live-safe keys is applied, a change to any other key is recorded as awaiting restart, every outcome is an audit event, and the environment still overrides the file.
17. A configuration file that may never hold secrets or insecure switches: such keys, and any unknown key, make start-up fail rather than be ignored.
18. Service files live under an unlisted per-tenant directory with long random file names as a location-secrecy barrier (stated limit: no per-file OS permissions).
19. (Cargo feature `clustering`, experimental, unused by default) Multi-server replication using vector clocks, conflict resolution, heartbeat failover and session persistence.

### Hit 12 in detail: US 8,127,174 B1 against commy's byte-range mirrors
Flagged by the sdk lane and the `dirty-ranges` lane; on board 296(A). The question the PM asked: does commy's replication to a mirror amount to *a backup of checkpoint data*?

The patent's own words (Google Patents description, 2026-10-25): *checkpoint data* "is essentially the data being used by software at particular times"; backup software "takes a 'snapshot' of the data and the server state, then stores that information as checkpoint data"; a *backup server* is "another server in the server cluster", the other cluster servers "are deemed backup servers vis-à-vis the production server"; "it is assumed that an initial backup of all the checkpoint data has already occurred", later backups copy only modified pages or blocks. It also says the file system "need not be accurate in tracking the modified portions".

Independent claims 1 (method), 9 (system), 15 (medium) have the same six elements; claim 21 (method) replaces the "initial backup / identify modified since" elements with read-only protection plus fault tracking. Commy code at origin/main d27e1f6, files under `src/server/` unless stated:

| claim element (claims 1, 9, 15) | what commy does | verdict on this element |
|---|---|---|
| (a) accessing checkpoint data | The service file is opaque bytes; the server never knows what they mean (`README.md`; `lib.rs:22-23`: "what the bytes mean is up to the clients"). A client may well store checkpoints in it, but nothing in commy designates, snapshots or records "checkpoint data" or "server state" | **not met by commy's code; depends on what a user stores** |
| (b) mapping the checkpoint data to a memory region | The server reads and writes the file with `std::fs` (`ws_handler.rs:529`, `:936`), not a mapping. Clients on the server's machine map the file themselves (`local_mapping.rs`); `lib.rs:25-57` maps with `memmap2` | met only by the client side (local mappers) and only if the bytes are checkpoint data |
| (c) initiating a backup of the checkpoint data after an initial backup has been performed | `Resync` (`ws_handler.rs:498-560`) sends the whole file to a client that asks, then later flushes follow (`commit_flush`, `ws_handler.rs:821`). That has the *shape* "full copy, then increments". But it is requested by a client that wants a live mirror, nothing in commy is called or acts as a backup, and mirrors are not told to keep a prior state | **arguable; the closest element** |
| (d) identifying data in the memory region modified since the initial backup | The server does not identify modified data: it takes the ranges a writer reports (`RangesChanged`, `ws_handler.rs:563-590`) or receives them as range frames (`handle_range_frame`, `ws_handler.rs:~883-950`) and merges them (`forwarding.rs:135`). Detection is done by the writing client (SDK, `dirty-ranges`: page-fault trapping or scan) | met only by the SDK / `dirty-ranges` (their records), not by this server |
| (e) copying that data | `read_frames` (`forwarding.rs:154-167`) reads the changed ranges from the file | met in the ordinary sense |
| (f) replicating that data to at least one backup server | The server forwards range frames to each remote member (`commit_flush`, `ws_handler.rs:821-879`, `Mode::Remote`). The receivers are application clients holding live mirrors that read and write, not servers that exist to hold a backup; the patent's backup server is a cluster peer of the production server | **the main difference; arguable** |

Claim 21 adds: set all portions of the region read-only, track write faults, treat faulted portions as modified. That is exactly the page-fault write trapping that `dirty-ranges` does in a client process; the server does none of it. Whether a commy *deployment* (SDK + `dirty-ranges` + this server) performs claim 21 turns on the same two terms, "checkpoint data" and "backup server".

**Assessment (not a legal opinion).** The method steps are performed by different pieces (writer client: map, trap, report; server: copy, forward; mirror client: receive), and the two limiting terms, *checkpoint data* and *backup server*, describe an application-failover product: periodic snapshots of an application's state replicated to a standby cluster node. Commy's mirrors are live shared views, not backups, and nothing in commy stores or labels checkpoints. On the claim language alone the overlap is on (c)-(e) in shape and not on (a) and (f) in kind, so my read is that commy does not practise these claims as designed. Two things keep this `needs-review` rather than `clear`: (1) a user who stores application checkpoints in a service and mirrors it to a standby server would arguably perform every element with commy as the carrier (an inducement / contributory question for a lawyer, not for this lane); (2) the claims were read in Google Patents' machine-converted text, prosecution history was not available, and "backup server" and "checkpoint data" may have been construed in ways this lane cannot see. Options for the PM and CireSnave: accept the risk; add a documentation note that commy is not a checkpoint/backup system (no effect on the claim, but no inducement by documentation); or get a lawyer's read before release 1.0.
